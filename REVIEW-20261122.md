## HIGH

### H1 — Verdict DEMO bisa di-replay oleh run LIVE
`src/guard.ts` — replay memakai kunci idempotensi yang sama untuk demo dan live; `scripts/demo.ts` menulis ke `evidence/verdicts/` default yang sama dengan run live. Skenario: `npm run demo` menyimpan GO 100/100 untuk WETH; run live `guard` kontrak yang sama di hari yang sama langsung me-replay verdict demo tanpa membeli cek apa pun, lengkap dengan `verdictHash` yang tampak sah. Evidence JSON demo berlabel `minerName: "demo (simulated…)"`, tapi `renderVerdict`/CLI tidak menandai replay-demo secara mencolok.
Perbaikan: namespace terpisah — demo menulis ke `evidence/verdicts/demo/` (atau kunci berisi `demo:`), replay hanya live-ke-live; dan/atau `replayed` + `simulated` ditampilkan jelas di output CLI. Tambah tes: demo lalu live kontrak sama → live TIDAK replay.

### H2 — 402 setelah pembayaran di-retry DAN tidak dihitung sebagai terbayar
`src/telegraph.ts`, `attempt()`: jika paid request (X-PAYMENT sudah terkirim) dijawab 402, `fail("refused", …)` dipanggil tanpa `paidUusdc` → `billing: "none"`, padahal uang mungkin sudah tertagih. Karena `"refused"` ada di `RETRYABLE`, `ask()` me-retry dengan challenge+nonce baru → tanda tangan & bayar kedua. Melanggar janji guard ("paid-but-failed never retried", "counted against the ledger"). Jalur 5xx/4xx lain sudah benar (melewatkan `sent` → `billing: "unknown"` → tidak retry).
Perbaikan: lewatkan `sent` ke `fail("refused", …, 402, sent)`; keluarkan `"refused"` dari `RETRYABLE` untuk kegagalan pasca-bayar (atau pisahkan retryable pra-bayar vs pasca-bayar). Tambah tes mock-fetch untuk jalur ini.

## MEDIUM

### M1 — Fallback bisa menagih jauh di atas klaim "$0,03/run"
`src/guard.ts`, `runCheck()`: dokumen bilang "retry SEKALI ke satu miner fallback", tapi kode mengulang semua 3 miner fallback sampai satu `ok`, dan TIDAK mengecek `answerUsable()` pada jawaban fallback. Worst case per cek: canonical terbayar tapi tak usable + 3 fallback terbayar = sampai ~$0,20/cek, ~$0,60/run — 20× klaim. Quote hanya menghitung 3×$0,01.
Perbaikan: batasi 1 fallback (sesuai dokumen) atau beri anggaran fallback eksplisit di `quote()`; terapkan `answerUsable()` ke jawaban fallback; catat biaya fallback di verdict.

### M2 — GO bisa keluar walau receipt/signal tidak terverifikasi
`src/fusion.ts` + `src/guard.ts`: `receiptProblems` (termasuk `"no receipt"`) dan `signalStatus: "missing"/"mismatch"` hanya menambah `openRisks`/alasan — verdict tetap bisa GO 100/100.
Perbaikan: turunkan verdict bila `receiptProblems` non-kosong atau signal `missing/mismatch` (cap skor / paksa HOLD), dan dokumentasikan aturannya.

### M3 — Kunci idempotensi mengabaikan `calldata`
`src/ledger.ts`, `idempotencyKey()`: kunci = chain + contract + value + to + hari. Dua tx berbeda ke kontrak sama (fungsi berbeda, mis. `mint` vs `transfer`) di hari sama akan me-replay verdict pertama.
Perbaikan: masukkan hash `calldata` (dan `label` bila memengaruhi pertanyaan) ke kunci.

### M4 — ABSTAIN akibat quote ditolak ikut ter-cache dan memblokir retry
`src/guard.ts`: bila `quote()` gagal (upstream down / total cap tercapai), `guard()` tetap `seal()` verdict ABSTAIN $0 — run berikutnya di hari sama me-replay ABSTAIN itu meski kondisi sudah berubah.
Perbaikan: jangan seal/cache run yang gagal di quote (atau tandai `cacheable: false` dan lewati replay untuk verdict itu).

### M5 — Parser CLEAN tidak negation-aware
`src/fusion.ts`, `parseFinding()`: pola blocker diuji pada `positiveText` (klausa `no…`/`not…` dibuang), tapi `CLEAN_PATTERNS` diuji pada `text` mentah. Jawaban miner "this contract is **not safe**" / "**not clean**" cocok dengan `/safe/i` / `/clean/i` → PASS, risk 0.
Perbaikan: uji pola CLEAN pada `positiveText` juga (atau tolak bila ada `not (safe|clean)`); tambah tes: `"not safe"`, `"not clean"`, `"never safe"` → bukan PASS.

### M6 — Ledger korup diam-diam me-reset cap $1
`src/ledger.ts`, `loadLedger()`: JSON korup / file terpotong → kembali `{totalUusdc: 0}` tanpa error. `saveLedger()` menulis langsung (non-atomik).
Perbaikan: tulis atomik (temp file + rename); bila ledger korup, gagal tertutup (tolak spend).

### M7 — Total cap hanya dicek di quote, bukan saat mencatat spend
`src/guard.ts` + `src/ledger.ts`: `quote()` cek `canSpend(ledger, 30_000)` sekali sebelum 3 ask paralel; tiap ask bisa menagih sampai $0,05 dan fallback menambah lagi — total riil bisa melampaui $1 sampai ~$0,12–0,60. `recordSpend()` tidak memeriksa cap.
Perbaikan: cek sisa cap di `recordSpend`/`countSpend` dan tolak mencatat/melebihi (atau peringatan keras + hentikan ask berikutnya bila cap terlampaui di tengah run).

### M8 — Template escrow rapuh terhadap trailing newline
`src/telegraph.ts`, `parseTemplate()`: panjang baris harus persis `2 + 8`; bila template live diakhiri `\n`, `split` menghasilkan baris kosong ekstra → `ChallengeMismatchError` → semua paid ask gagal.
Perbaikan: `trimEnd()` template sebelum parse (atau toleransi baris kosong akhir); tambah tes trailing-newline.

## Alur x402 — dinilai (statis, tanpa live)
Benar: validasi challenge (network CAIP-2, konsistensi `payTo` accept-vs-template, payee terkonfigurasi, konsistensi amount/resource, aset USDC, cap $0,05), signing EIP-191 via `viem` `personal_sign`, header `X-PAYMENT` base64 `{x402Version: 2, scheme: "escrow", …}`, receipt dari `x-payment-response` di-cross-check (payer/amount/rail/miner), verifikasi `GET /engine/v1/signal/<hash>`, tidak retry setelah bayar (kecuali celah H2), fail-closed ABSTAIN bila required check ERROR. Pre-season guard (tolak paid call sebelum 1 Nov 2026) sudah lewat tanggalnya tapi tidak berbahaya.

## Open item payee escrow (0x72a7… vs Diamond 0x3624…)
Client benar menolak payee tak dikonfigurasi — terbukti di kode + tes (`signEscrowPayment()` melempar `ChallengeMismatchError` bila `accept.payTo ≠ expected.payee`; tes "refuses a challenge paying an unknown address" memakai persis `0x72a70e…` vs default Diamond). Konsekuensi: dengan konfigurasi default, bila challenge ask live memang menyebut 0x72a7…, ask berbayar pertama akan GAGAL (mismatch) — aman, tapi demo live terblokir sampai payee dikonfigurasi. Itu fail-closed yang benar, bukan bug.
Cara memverifikasi settler yang benar tanpa probe berbayar ($0, tanpa signature):
1. **Probe POST unpaid `/engine/v1/ask`** — decisive. POST tanpa `X-PAYMENT` hanya mengembalikan 402 challenge; tidak ada tanda tangan/pembayaran. Butuh persetujuan proses (dulu timeout tanpa jawaban, bukan ditolak).
2. GET 402 sudah memberi sinyal (0x72a7…), tapi itu respons gateway generik — belum tentu sama dengan challenge ask-spesifik.
3. Verifikasi on-chain read-only (belum dilakukan): cek sumber/bytecode `0x72a7…` di Sepolia Etherscan/Sourcify — apakah itu kontrak settler/escrow Telegraph (fungsi `transferWithAuthorization`/settlement, event), siapa deployer/creation tx-nya, dan apakah Diamond `0x3624…` mereferensikannya. Bandingkan dengan Diamond.
4. Dokumen publik: pencarian web tidak menemukan dokumen resmi Telegraph yang menamai alamat settler — whitepaper hanya menjelaskan escrow secara konseptual. Jangan jadikan ketiadaan ini sebagai bukti; sumber otoritatifnya adalah challenge live (poin 1) + verifikasi on-chain (poin 3).
5. Hipotesis: dalam skema escrow x402, `payTo` di otorisasi belum tentu sama dengan vault deposit — `0x72a7…` bisa jadi settler/facilitator (penerima otorisasi EIP-3009) sementara Diamond adalah vault deposit. Bila benar, `fund.ts` (approve + `depositUSDC` ke Diamond) tetap benar, dan yang perlu diubah hanya `TELEGRAPH_ESCROW_PAYEE`. Jangan set env itu sebelum poin 1/3 mengonfirmasi.

Skor 100/100 dan 29/100 adalah artefak fixture, bukan pengukuran.

1. Payee challenge live (probe unpaid dulu) + 1 ask berbayar end-to-end: 402 → sign → receipt → `signal_hash` → `GET /signal/<hash>` = verified, untuk ketiga intent.

3. Biaya riil per ask dan perilaku fallback di kondisi live.
4. Receipt + signal benar-benar cocok dengan yang ditandatangani.
5. Jalankan ulang `npm test` + `tsc --noEmit` dan tambah tes untuk H2/M1/M5 sebelum live.
